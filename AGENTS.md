# Release versions

The current release package version is 1.1.4. During ordinary development, keep the current extension version unchanged. Update the version only when the user explicitly requests a new version; use their specified version when provided, otherwise increment the patch version. Keep package.json, the root package-lock.json version fields, installation instructions, CI package paths, and the latest changelog entry consistent. Do not change third-party dependency versions when updating the extension version. Do not move or overwrite an existing remote tag without explicit authorization.

The user's phrase “发布新版本” authorizes this default release workflow: update the version and release documentation, run relevant checks, commit the pending project changes together, create an annotated Git tag matching the version (for example 1.1.4), push the branch and the new tag, then archive old artifacts and generate/verify the new VSIX. Verify the remote branch/tag against the local commit, and test the actual installed VSIX before handing it over. If the version or tag already exists, choose the next unused patch version rather than replacing a historical tag. This workflow does not include Marketplace publishing unless requested.

During ordinary development, keep pending edits uncommitted until the user explicitly requests a combined commit or invokes the new-version release workflow. Rebuilding a VSIX without a new-version release request does not implicitly authorize a Git commit or push.

Before generating a release package, archive existing VSIX packages and their checksum/validation files under a timestamped dist/archive/ directory. Name new packages with the extension name and version only (for example wanguo-sourceinsight-reader-1.1.4.vsix); never append feature or fix names. Use npm run package so the archive step runs before building. Preserve archived package bytes and historical tags.
